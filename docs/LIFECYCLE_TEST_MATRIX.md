The macOS/Windows/Linux column entries below were derived by reading the current implementation, not by running these scenarios; treat each as a hypothesis to confirm on hardware, not a substitute for doing so.

## Standalone phone delivery

There is no CI equivalent for these: notification delivery in a simulator or
emulator does not predict a real device, and the whole point of this path is
that it works while the app is **not** running. Every row must be confirmed on
physical hardware before a mobile release.

Run the first block with **no watch paired at all**, on both an iPhone and an
Android phone.

| #   | Scenario                                   | Expected                                                 | Result |
| --- | ------------------------------------------ | -------------------------------------------------------- | ------ |
| 1   | Break falls due with the app backgrounded  | Notification arrives on time                             |        |
| 2   | Break falls due with the screen locked     | Notification arrives on time                             |        |
| 3   | Break falls due in airplane mode           | Notification arrives; nothing depends on a network       |        |
| 4   | Reboot the device, then wait for a break   | Reminder still arrives (chain re-armed)                  |        |
| 5   | Reopen the app after a break notification  | Phase matches the notification; timer is **not** paused  |        |
| 6   | Change the work interval                   | Old reminders do not fire; new ones reflect the change   |        |
| 7   | Pause the timer                            | All pending reminders are cancelled                      |        |
| 8   | Wait through a period outside active hours | Nothing fires                                            |        |
| 9   | Deny notification permission               | Settings shows the warning; no silent failure            |        |
| 10  | Android: revoke exact alarms               | Reminder still fires; Settings reports inexact precision |        |
| 11  | Leave the app closed overnight             | One break due on reopen, not a burst; counters are sane  |        |

Then **connect a watch** (`watch_enabled` on) and confirm the routing:

| #   | Scenario                                   | Expected                                     | Result |
| --- | ------------------------------------------ | -------------------------------------------- | ------ |
| 12  | `alert_target = phone`                     | Phone alerts; watch stays silent             |        |
| 13  | `alert_target = watch`                     | Watch alerts; phone stays silent             |        |
| 14  | `alert_target = both`                      | Both alert                                   |        |
| 15  | Turn `watch_enabled` off                   | Watch stops alerting within one revision     |        |
| 16  | Watch out of range, `alert_target = watch` | Watch still alerts from its own offline plan |        |

And confirm desktop is untouched:

| #   | Scenario                            | Expected                                      | Result |
| --- | ----------------------------------- | --------------------------------------------- | ------ |
| 17  | macOS and Windows settings          | No Wearables section, no alert-target control |        |
| 18  | Desktop settings store after a save | Contains no `watch_*` keys                    |        |

## How to use this

For each cell, either confirm the "Known" behavior really holds on real hardware, or replace it with what was actually observed. Cells marked **Gap** need investigation before they can even be tested meaningfully. Do not publish a signed release draft with unconfirmed rows in this table for the platform being released.
